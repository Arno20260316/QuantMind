# 推理落库慢 · 成交台账双写 —— 修复细案

> 状态：已实施（2026-10-13）
> 范围：`backend/services/engine/inference/` + `backend/services/engine/qlib_app/utils/` + `backend/services/api/routers/model_training.py`
> 依据：容器内实测取证（延迟基准、Redis 键分布、PG EXPLAIN、真实 `CnExchange` 复现）

## 一、问题与实测证据

### 1.1 落库慢：5 分 09 秒/任务，其中 ~96% 是空转

单任务时间账（3206 只标的，2026-10-12 Celery 日志）：

| 阶段 | 位置 | 实测 | 占比 |
|---|---|---|---|
| Step 0.1 保留期 DELETE | `script_runner.py` | 1.15 s | 0.4% |
| Step 2 逐股 hget + 逐行 INSERT | `script_runner.py` | ~148 s | 48% |
| Step 3 逐股 hget（**第二遍**）+ 逐行 INSERT | `script_runner.py` | ~148 s | 48% |
| 其余 | | ~1 s | |

**根因不是「慢的 I/O」，是读了一个已退役的键命名空间 + 连错库，两条叠加**：

```
远端行情 Redis（www.quantmindai.cn:6379）
  db0（代码实际连的，未传 db= 的默认库）  market:snapshot:*  n=0     ← 恒查空
  db3（写侧与其余消费方落库）            market:snapshot:*  n=657   ← 写侧契约键
  db3 中 stock:*                           n=0                   ← 键名也是退役命名空间
```

两条错各自都足以让取价恒空：键名 `stock:{code}.SH` 无人写，且连接漏传 `db=`（
`resolve_remote_quote_redis()` 返回的第 4 元 `_db` 被解包后丢弃）连到 db0。
实测：同一 client 不传 `db` → `{}`；传 `db=3` → 三只全中（`2026-10-13` 盘中）。

实测延迟：远端 `hget` 单次 46 ms → 3206 次 = 148 s；本地 Redis 单次 0.05 ms。
因键不存在，**`engine_signal_scores.expected_price` 全库 14,417,198 行 100% 为 NULL**，
`qm_research_candidate_snapshot` 4,018,463 行同样 100% NULL。两次查询从未产出过任何值。

另有两处真实但不占大头的缺陷：
- 保留期 DELETE 走 **Parallel Seq Scan**（`Rows Removed by Filter: 4,805,733`，1.15 s/次），
  因为 `_PREDICTION_RETENTION_DAYS` 默认 730 天 → 谓词恒不可命中，且现有 6 个索引无一覆盖
  该五元组；代码注释却写「默认 30 天」。
- `_INFER_PERSIST_LOCK` 是**进程内 `threading.Lock()`**，Celery `--concurrency=4` prefork
  下 4 个 fork 各持一把，对「多 worker 并发写库」零保护。

### 1.2 成交台账双写：同一 `deal_order` 被调两次，只对卖单

用真实 `CnExchange` + 桩 `Exchange.deal_order` 复现（同一步、同一个卖单）：

```
ledger rows after executor path (真实成交): 1
ledger rows after strategy path (估现金)  : 2
```

机制（qlib 0.9.7，`pyqlib-0.9.7.dist-info/RECORD` 校验 `signal_strategy.py`/`executor.py`/
`exchange.py` 均 MATCH，未被本地改动）：

1. `TopkDropoutStrategy.generate_trade_decision`（`signal_strategy.py:258`）对**每个卖单**
   调 `deal_order(sell_order, position=current_temp)` 估可用现金 —— 这里的 `position`
   是 `copy.deepcopy(self.trade_position)`，**不是真实账户**；
2. `SimulatorExecutor._collect_data`（`executor.py:604`）对同一个 `Order` 再调一次
   `deal_order(order, trade_account=self.trade_account)` —— 这次才是真实成交；
3. 买入腿只调 `get_deal_price` / `get_factor`，**不调 `deal_order`** → 只有卖单翻倍。

线上分布与之一致：52 个键 80,767 条记录、重复 24,940 条（30.9%），
**方向分布 `{'sell': 24940}`，买组 0**；两份副本仅 `timestamp` 差 ~8 ms，
列表位置差 = 卖单批大小。

`risk_analyzer._deduplicate_trades`（以 `amount+commission` 为主键）**完整吃掉**了这 2.4 万条
——这是为什么它从初始提交 `a8c37035` 起就存在：它是补丁，不是根治。

## 二、修复方案

### 2.1 行情取价：批量 + 契约键（`script_runner.py`）

- 键构造统一走 `decision_context_source.snapshot_key()`（= 写侧契约
  `market:snapshot:{prefix.lower()}`），删掉两处手拼的 `stock:{code}.SH` 前缀。
- **连接透传解析出的 `db`**（`resolve_remote_quote_redis()` 第 4 元）。原来解包成 `_db`
  就丢弃 → 连到 db0 恒查空。同族消费方（`remote_redis_source` /
  `manual_execution_service` / `real_trading_utils` / `simulation.redis_series_quote`）
  均已正确透传，唯此处漏。
- **两次逐行查询（Step2/Step3）合并为一次批量**：Step2 前对全量 symbols 用
  `pipeline(transaction=False)` + `hget(key, "Now")` 分片（每片 200 键，同 `realtime_service` 口径）
  取价一次，Step3 复用结果。
- 失败降级：连接失败 / pipeline 异常 → 返回已取到的部分（缺的不入表）并 **WARNING 留痕**
  （不再是 `debug`/静默 `pass`）；调用方据此把 `expected_price` 写成 NULL。
- 实测：3206 键 pipeline ≈ 1.6 s（远端）、0.17 s（本地），对比原 296 s。

### 2.2 保留期 DELETE：加存在性探针（`script_runner.py`）

先跑索引友好的 `SELECT 1 ... LIMIT 1`（走唯一索引，实测 ~0.3 ms），
命中才执行 DELETE，未命中原样返回。语义完全不变（默认 730 天下永远不删），
只是不再为一次注定空转的删除付全表顺序扫。

### 2.3 失效锁与失实注释（`script_runner.py`）

- 删除 `_INFER_PERSIST_LOCK`（进程内锁在 prefork 下无跨进程语义；实际串行由
  Redis `inference_lock` + 单线程补全循环保证）。保留并重写注释说明「写库内并发控制现状」。
- 修正保留期注释（730 天默认值与 env 名）。

### 2.4 补全的断点续跑（`model_training.py`）

`pred_signals` 原本全程累积在内存、**循环结束后**才合并进 `pred.parquet`，中途重启即丢失
已算完的天数。改为**每日落一次** `merge_signals_into_pred`（同日幂等 upsert），
并删除「runner 失败 → 复制上一日行、只改 `trade_date` 重标」的模板复制兜底：
那是用旧分数冒充新日分数，属数据完整性问题；失败日如实记 `failed`。

### 2.5 成交台账：只记真实成交（`cn_exchange.py`）

`CnExchange.deal_order` 只在 `trade_account is not None`（真实账户成交）时写流水。
策略层估现金传的是 `position=`（deepcopy），天然不落流水。
`_deduplicate_trades` 保留为兜底（历史键已写入的重复仍需折叠）。

## 三、验证

- 单元：`test_inference_persist_perf.py`（键契约 / 批量取价复用 / 探针短路 / 连接失败留痕 /
  成交只记真实账户）、`test_backfill_daily_merge.py`（逐日落盘 / 无模板复制）。
- 回归：`backend/run_tests.py all`，判据 = **零新增失败**。
- 实弹（待开盘窗口）：单日推理任务墙钟由 ~5 分 09 秒降到 ~15 秒以内，
  且 `expected_price` 首次出现非空值。
